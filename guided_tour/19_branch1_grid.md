## Speech (verbatim)

**Stop 19 of 29: Branch 1, the pass/fail grid.** Open on the side: `tools/verdict_criteria_evaluator.py`, `tools/residual_ic.py`, `tools/composite_cache.py`, `tools/fold_confirm.py`, `tools/explore_confirm.py`, `run_phase1_research.py`, `docs/DATA_DICTIONARY.md` (§7, §9), run_102's `grid_evaluation.yaml`, `idea_status.yaml`, `residual_ic.yaml`, `fold_confirmation.yaml`.

**In one sentence.**
The grid is the judge of the idea: it grades every pre-registered criterion on every variant (a table of pass or fail), and turns that table into one status, validated, refuted or inconclusive.

**Why it exists.**
After a backtest, there is always a story that makes the result look good. The grid removes the story: it reads only the criteria written before the backtest (the pre-registration), applies them mechanically, and writes one status.
It is the only one of the three branches that decides what happened to the idea. A second check, fold confirmation, asks whether the belief that started the idea held on test months it had never seen.

**What comes in, what goes out.**
- In: each graded variant's results (stop 18); the pre-registration's pass rule (stop 08); the campaign's proven pieces (for the overlap criterion); the claim that started the run (for fold confirmation).
- Out: `grid_evaluation.yaml` (the table), `idea_status.yaml` (the status), `residual_ic.yaml` (the overlap measure or why it was skipped), `fold_confirmation.yaml` (the claim on the new fold), and a row in the campaign's confirmation list.
- Next: the status ends the run (stop 23) and is recorded in campaign memory (stop 22); decide-next reads it (stop 24).

**What happens here, step by step.**
1. If the overlap criterion applies, code measures how much information each variant adds over the campaign's proven pieces (a rank correlation of what is left after removing the proven forecast). With no proven piece on this bar size, it is skipped with that reason.
2. The whole-test Sharpe ratio (return per unit of risk over the chained test) is added for any criterion that needs it.
3. For each criterion and each variant, the grid computes the measure over the windows (for example the median of the windows' values), compares it with the threshold, and writes PASS, FAIL or INCONCLUSIVE (not enough data: too few windows, too few trades).
4. The status: any FAIL with enough data refutes the idea. No FAIL but a missing cell, or not every variant graded, or a variant run on partial data: inconclusive. Every cell PASS on every variant: validated.
5. The status is written with a fixed routing label (validated → promote, refuted → kill, inconclusive → a person decides); under today's switches the run ends on the status alone.
6. Fold confirmation: for a run built from an earlier run's claim, the claim's test is measured on this run's fold and graded by a "noise rule": the pooled effect must have the claimed sign at every horizon, and hold in all windows but one (at least 4). Confirmed, not confirmed, or not measurable. One row is added to the campaign's confirmation list.

Example: run_102's grid has one criterion, forecast quality at 24 hours (median above 0.02): XRP passed (0.0286), base failed (-0.0084), the halved-weight variant failed (-0.0136), LTC failed (-0.0003). One FAIL with enough data: `idea_status: refuted`. The overlap criterion was skipped ("no forecast block on this timeframe"). Fold confirmation of run_101's claim on fold B: `not_confirmed` (the claimed sign held in 3 of 6 windows at 24 hours).

**What it costs and how long it takes.**
No AI call; computed right after the backtests.

### (1) Design and mechanism

1. The grid itself is the sound judge the speech describes. The pass rule is resolved against the menu with the pre-registered fields winning (`vce:1798-1814`), a malformed criterion short-circuits to `SPEC_ERROR` with `idea_status: None` rather than a guess (`:2257-2274`), FAIL dominates INCONCLUSIVE (D-014, `:2276-2285`), a failed or untested variant caps the idea at inconclusive (`:2286-2288`), the status file is closed by schema (`idea_status.schema.json:9`, `:23-41`), and three readers re-check it: the route refuses a missing or stale file (`RP:4584-4600`), the memory refuses a grid that disagrees with `idea_status.yaml` (`campaign_memory.py:823-828`), the launcher refuses a `completed_<status>` whose file reads another status (`RC:295-310`). A story cannot change the status after the fact.
2. The live criterion has no significance gate; the criterion that never runs has one. A window-source cell is the median of six window values against the threshold with a floor of 5 windows and no p-value (`vce:1446-1493`; menu `criterion_menu.yaml:192-193`). The residual-IC cell adds n_eff and a one-sided block-adjusted p with the stated reason "with n_eff barely at its floor, a pure-noise block clears a 0.01 IC threshold about half the time, the p gate stops it" (`:1579-1583`, `:1625-1631`; `residual_ic.py:19-23`, `:295-297`). The same argument holds for `forecast_ic_median` and is not applied. Today it does not matter (stop 08 note 1.1: no hourly variant has reached 0.02, so the threshold only refutes); the day a variant passes, the grid cannot say whether a 0.02 median over six autocorrelated windows is noise, while the code to say so sits in the next function.
3. The status is of the idea on every coin step 2 picked, not of the idea. Unanimity across columns (`:2280-2282`) means an asset variant on LTC or XRP can refute a BTC idea, and the speech's run_102 example is the mirror case (XRP passed, base failed, refuted). The cells survive in memory (`campaign_memory.py:186-187`: `cells`, `counts`), but `idea_status` and `tried_ideas` carry one word (stop 07 note 1.4), and decide-next reads only that word for status (`decide_next.py:76-78`). So which coins Haiku chose from coverage prose (stop 15 note 1.4) co-decides the verdict the loop remembers. Consistent with falsification-first; it means a refutation says "the variant set failed", and the loop cannot tell that from "the idea failed".
4. A grid failure fails the stage after the spend, not before. The grid runs inside the backtest tool stage (`RP:2447-2514`); an exception is caught, printed, and collected under `_sr_on` (`:1823`, `= _grid_route_enabled()`, on) into `_sr_errors`, which `_raise_specialist_readers_prereq_errors` raises at the end of the stage (`:2523`). Trial rows are already written (`:2404-2405`), so the luck count is kept. Fail-closed and correct; the 24 backtests are paid first, and the pre-registration's shape (menu-shaped or not, `:2450`, `:2507-2508`) is the one input that could have been refused at launch (stop 01 note 1.2).
