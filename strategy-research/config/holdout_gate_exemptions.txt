# holdout_gate_exemptions.txt - audited exemptions for holdout_date_gate.sh
#
# FORMAT:  <repo-relative-path><TAB><max allowed holdout-date lines>
#     or:  <repo-relative-path><TAB>PROSE      (running narrative files only)
#          '#' comments and blank lines ignored.
#
# WHAT AN ENTRY MEANS
#   "This file contains N lines carrying a date inside the sealed window
#   2026-01-01..2026-06-30, a human has looked at them, and they are PROSE, PLANS,
#   CONFIG or CODE -- not market data." The count is part of the exemption: a listed
#   file that gains an N+1'th holdout-date line is BLOCKED again, so the exemption is
#   pinned to audited content rather than to a filename. Unlisted file => blocked.
#
# THE PROSE MARKER (added 2026-08-18, Jeremy's call -- E-003 S2)
#   A handful of files exist to ACCUMULATE narrative about the seal: the research
#   ledgers, FORK_CHANGES.md, CLAUDE.fork.md. Every entry documenting a holdout
#   decision adds a holdout-date line -- the file doing its job -- which under count-
#   pinning re-blocks the gate until a human hand-bumps the number, forever. Measured
#   2026-08-08: 3 files blocking. Measured 2026-08-18: 7. That trend ends in routine
#   --no-verify, which this gate's own docstring calls worse than no gate at all.
#   Those files carry PROSE instead of a count: exempt by PATH, not by line count.
#   TRADE-OFF, stated plainly: a PROSE file is not scanned at all, so market data
#   pasted into one would not be caught here. Accepted because these are .md prose
#   files nothing writes programmatically, and the real risk (.csv/.json artifacts)
#   stays fully guarded.
#   PROSE IS FOR RUNNING NARRATIVE ONLY. Code, config, fixtures and data stay
#   count-pinned -- a test file gaining new sealed dates SHOULD get a human look.
#   Do not reach for PROSE to silence a blocked commit; the count is the default.
#
# WHY THESE EXIST (audited 2026-07-26, dispatch W5)
#   Every entry below was verified to be one of:
#     a) Pre-seal research plans under strategy-research/runs/** that NAME the window
#        they intend to reserve ("holdout: 2026-03-01 to 2026-06-16", walk-forward fold
#        boundaries, freeze dates). These predate or accompany the seal itself; naming a
#        window is the opposite of reading it.
#     b) Policy, docs, briefs, KB and session reports that cite the boundary in order to
#        enforce or explain it -- including campaign_data_policy.yaml, which necessarily
#        contains the literal holdout_range it defines.
#     c) Code and tests whose fixtures/constants reference the boundary, including
#        holdout_date_gate.sh and its own test, which cannot do their job without
#        containing the dates they detect.
#   NOT ONE is a data file: the audit confirmed 0 .csv/.ndjson/.tsv/.parquet files in
#   the residual, across 7,770 text files examined. The two run directories that DID
#   carry holdout bars were quarantined instead of exempted
#   (campaign_data_policy.yaml:holdout_contaminated_runs).
#
# HOW TO ADD AN ENTRY -- do not do this reflexively
#   Regenerate candidates with:
#     sh strategy-research/tools/holdout_date_gate.sh --report-residual
#   then, for each new path, READ the matching lines and confirm they are not market
#   data before pasting the path/count. If a file turns out to carry holdout bars, the
#   answer is to quarantine or exclude it, never to register it here.
