# Kraken data workstream: design (Q1 one-minute history, Q2 ingest, Q3 audit)

Status: design for operator review. Built tonight: the Q1 probe and the Q3 census extension. Q2 is design only.
Nothing in this document, the probe or the census writes into `trading-bot/local_data/`, changes the run pipeline, or runs a backtest.

Ids used below:
- CUL-250 / PR #133: the opt-in `fetch_interval_seconds` that lets the engine build coarser bars from a finer cache.
- CUL-274: a NaN in a rolling window is a gap signal, not a value.
- CUL-203: the seal guards on the engine's read path (`data_manager._holdout_bounds`, `_assert_no_sealed_rows`).
- E-054: the run's data availability gate (Layer 1, the capability table; Layer 2, the per-window data touch).
- D-042: a "different coin" variant may run when its coin covers about 60% of the windows.
- D-169: a window counts as covered only when the coin has twice `required_bars` of warm-up bars before it.
- D-180: the run viewer (`tools/run_viewer`).

Holdout rule for this document: the sealed window is named only as `holdout_range` in `config/campaign_data_policy.yaml`. No date inside it, and no date that marks its edges, appears here.

## 1. Verified facts

### 1.1 How a run finds price data today

The path, from the brief to the file:
1. The brief's `venue`/`product` goes to `tools/venue_resolver.py:98` (`resolve`). A Kraken brief becomes `exchange: kraken`, with the funding feed dropped (`:134`, `drop_feeds: ["funding_rate"]`). Symbols are renamed to the venue's form at `:142` (`venue_symbol`: BTCUSDT -> BTCUSD).
2. The protocol carries `exchange`. `tools/run_protocol.py` passes it to `run_backtest` (`:2584`, `:2657`).
3. `DataManager.fetch_historical_data` (`trading-bot/data/data_manager.py:1237`) builds a `HistoricalDataFetcher` (an alias of `CcxtFetcher`, `ccxt_fetcher.py:247`) at `self.fetch_interval_seconds` (`:1274`).
4. `CcxtFetcher.cache_key` (`trading-bot/data/fetchers/ccxt_fetcher.py:101-124`) names the file `"{symbol}_{tf}"` for Binance and `"{exchange}_{symbol}_{tf}"` for every other venue. Example: `kraken_BTCUSD_1h`.
5. `BaseFetcher._csv_path` / `_load_local` (`trading-bot/data/fetchers/base_fetcher.py:393-410`) read `local_data/<cache_key>.csv` whole, with `pd.read_csv`.
6. The seal guards run on the returned frame. Before the fetch, `_assert_request_window_unsealed` (`data_manager.py:1291`) checks the requested window. After the read, `_assert_no_sealed_rows` (`:1328`) checks the rows.
7. Before any backtest, the data gate (E-054) checks each window:
   - Layer 1 reads `config/venue_data_capability.yaml`: the Kraken spot universe at `:297-301`, and per-coin first bars at `:315-332`, generated by `tools/refresh_coin_start_dates.py:277`.
   - Layer 2 calls the same `fetch_historical_data` (`tools/data_availability_gate.py:714`) and grades `_missing_fraction` (`:538`) at 5% (`:106`, `:622`).
   - The per-variant record goes to `runs/<run>/artifacts/variants/<v>/data_availability_gate.yaml`, copied there by `workflow/run_phase1_research.py:1818-1910`.
   - Unfetchable data becomes rows in `campaign_record/data_requests.yaml`.
8. `config/coin_universe.yaml` names the instrument pivots. Kraken entries carry `exchange: kraken` and `cache_key` (for example SOL at `:31-41`, `cache_key` at `:35`).

Consequence: the run sees new data only through a file at `local_data/<cache_key>.csv`, plus the capability and universe entries. Q2 below changes none of the readers.

### 1.2 Timeframe rule

- The cache must exist at the exact timeframe unless `fetch_interval_seconds` is set (CUL-250).
- `DataManager.__init__` accepts `fetch_interval_seconds` (`data_manager.py:712-765`). It must divide the bar interval.
- `CandleBuilder.add_row` (`:447`) aggregates finer rows up to the bar.
- In campaign runs the value comes only from `trading-bot/config.json` `trading.fetch_interval_seconds` (`core/launcher.py:213`). `tools/run_protocol.py` never passes it (0 occurrences). So it is a global switch, not a per-run one.
- The gate mirrors that switch (`data_availability_gate.py:633`).
- `venue_data_capability.yaml:105-111` records the mechanism as wired, off by default.

Archive details that matter for the design:
- Full archive: 5 parts of about 2 GB each, about 10 GB in total (an estimate; the page gives no total).
- Quarterly incremental zips are published. There are no per-pair downloads.
- No header. Columns: unix seconds, open, high, low, close, volume, trades.
- Minutes with no trades are omitted ("only intervals with recorded trades are included").
- A copy of the full archive is already on disk:
  - path: `trading-bot/local_data/Kraken_batch/master_q4/`, 7,582 files, 16 GB extracted;
  - 1,522 one-minute files (`*_1.csv`), all 19 breadth pairs present;
  - it ends at the walk-forward extension's end (`campaign_data_policy.yaml:89-100`);
  - recon: `engineering/sessions/session_reports/20260721_kraken_archive_recon.md`.
  - Its download URL, time and part hashes were never recorded. It is the only provenance gap.
- The tranche that overlaps `holdout_range` is quarantined in `local_data/holdout_sealed/` (`campaign_data_policy.yaml:167-184`).
- Third-party aggregates (CCCAGG and similar) are a different venue and out of scope.

Recommendation:
- **Primary: the Kraken OHLCVT archive.** It is free, Kraken-native, has published SHA-256 sums, and is already on disk for the whole in-sample span.
- **Fallback: the REST Trades endpoint**, paged with the raw `last` nanosecond cursor through ccxt's implicit `publicGetTrades`. Do not use `fetch_trades`: it sends `since` in seconds (`ccxt/kraken.py:1520-1523`).
  - It fills pairs missing from the archive (HYPE).
  - It covers spans after the archive's last quarter, once the operator allows them.
  - It cross-checks archive days.
- ccxt `fetch_ohlcv` is out: it can never reach more than 12 hours of 1m.

The policy has no rule written for fetching. What it does say:

The archive tranche was moved into `local_data/holdout_sealed/...`, registered `sealed: true`, `single_use: true`, and the reachability re-check confirmed that no in-sample loader reaches `holdout_sealed/**`.

- After the seal, the code disagrees with itself:

  - The policy says nothing about OHLCV after the seal end.
- The exploration boundary used by every fetch in this workstream: **strictly before the `holdout_range` start**, read through `tools/holdout_policy.py`. It is the stricter of the two readings and matches `check_windows_before` (`holdout_policy.py:192-226`).

## 2. Q1: one-minute history

### 2.1 Source

Use the archive (1.3). For the in-sample span the "backfill" is an ingest of files already on disk: 0 requests.
- Re-verifying the copy byte-for-byte against Kraken's published hashes means downloading the 5 parts again: about 10 GB, against about 8 GB free on C: tonight.
- The probe instead cross-checks one day against the Trades endpoint and records the copy's own SHA-256 (2.6).

### 2.2 Download step (archive; only on "fetch approved <scope>")

1. Fetch `OHLCVT_Full_PARTS_SHA256SUMS.txt`, or the quarterly zip's published hash.
2. Download each part to `<staging>/download/<part>.partial` with HTTP Range resume.
3. Checkpoint file `<staging>/download/checkpoint.json`: bytes done per part. Progress log: one line per 100 MB.
4. Verify SHA-256 against the published sum, then rename `.partial` to its final name.
   - A mismatch deletes the part and retries, with backoff 2, 4, 8, 16 s; 4 retries in total.
5. Assemble and unzip into a new, empty directory. Read the files as untrusted data (no interpreter runs from that directory).
6. Before any file leaves the unzip directory, split each pair's rows at the holdout start (policy helper). Decision 1 decides where the rows at and after it go.

### 2.3 Trades loop (fallback; only on "fetch approved <scope>")

- Cursor: `since` (ns) taken from the previous response's `last`.
- Checkpoint `<staging>/<pair>/checkpoint.json` holds `{last, trades_written, minute_flushed}`. A resume restarts from `last`.
- Rate: ccxt `enableRateLimit=True` plus at least 1 s between calls.
- Errors: `EAPI:Rate limit exceeded` and network errors back off 2, 4, 8, 16 s. After 4 failures the loop stops with the checkpoint intact.
- Writes are idempotent. Closed minutes are flushed to a per-day file through a temp file and an atomic rename. A minute is closed when a trade from a later minute is seen.
- Stop rule: the cursor passes the exploration boundary. No trade at or after it is kept or printed.
- Cost: measured by the probe (2.6). Requests per day equal trades per day / 1000.

### 2.4 Storage (decision 2)

CSV at 1m for years is the wrong format: the 19 one-minute archive files hold the rows measured in 2.6, and the engine reads a CSV whole on every backtest (`base_fetcher.py:406`).

Proposal:
- Layout: `local_data/kraken_1m/<cache_key>/<YYYY>.parquet`, for example `kraken_1m/kraken_BTCUSD_1m/2023.parquet`. One file per coin per year. The cache key stays `CcxtFetcher.cache_key` unchanged.
- Columns:
  - `timestamp`: int64 ms, UTC;
  - `open`, `high`, `low`, `close`, `volume`: float64;
  - `trade_count`: int32.
  - The 12-column Binance padding written by `ingest_kraken_archive.py` (`:145-158`) is dropped at 1m.
- Compression: zstd. A sidecar `<YYYY>.provenance.json` per file holds source, URL or endpoint, fetch time, SHA-256 and row count.
- Reader: one branch in `BaseFetcher._load_local`. When `<data_dir>/kraken_1m/<cache_key>/` exists and no `<cache_key>.csv` does, it reads only the years the request window touches.
  - It is opt-in by the directory's presence. Every existing cache keeps its path and bytes.
  - The CUL-203 guards still run on the returned frame.
- Cost:
  - Parquet needs `pyarrow`, which is not in the venv: one new dependency, operator's word needed.
  - The no-dependency fallback is the same layout with `<YYYY>.csv.gz`, read by pandas, slower.
  - Size estimate: 2.6.

### 2.5 Validation on write (shared by Q1 and Q2)

Implemented in `tools/kraken_1m_probe.py::validate_minute_frame`. The report's `passed` is false when any of these counts is non-zero, and the Q2 ingest refuses the write then (the probe itself only reports):
- off-grid timestamps;
- non-increasing steps;
- duplicates;
- NaN;
- OHLC violations: low above min(open, close), high below max(open, close), low above high, or a price at or below 0;
- negative volume;
- `trade_count` below 1 or not an integer;
- sealed rows (counted through the policy, never printed).

Missing minutes are reported, not refused: the archive omits no-trade minutes by design. The report gives a histogram (1, 2-5, 6-60, 61-1440, over 1440 minutes) and the longest gap.

## 3. Q2: ingest command (design only)

One command, two steps, modelled on the operator's checkout sync (merge-tree and commit-tree, one approval paste naming the commit).

`strategy-research/tools/data_ingest.py stage --source <file> --venue kraken --symbol BTCUSD --timeframe 1m|1h|1d --stage <dir outside the repo>`
1. Read the source as untrusted data. Accepted schemas:
   - the Kraken archive's 7 headerless columns;
   - the cache's own 12-column schema;
   - the trades probe's 7 columns.
2. Timestamps: unix seconds or ms, or ISO strings with an explicit UTC offset. A naive ISO string is refused unless `--assume-utc` is given; refused, not guessed, because `base_fetcher` already refuses tz-aware frames on read.
3. Validate with 2.5, on the timeframe's grid.
4. Rows at or after the holdout start are refused outside the sealed store. Refuse means the command stops and writes nothing; only the count is printed. Decision 1 may add `--sealed-store`, which writes those rows only under `local_data/holdout_sealed/<tranche>/`, by the named procedure.
5. Write under the engine's name, `CcxtFetcher.cache_key(symbol)` (`ccxt_fetcher.py:101-124`). For 1h/1d the converter is `ingest_kraken_archive.ingest(..., data_dir=<stage>)` (`:347`), reused unchanged except for the message fix in 1.5. For 1m the format is decision 2. The output goes into `<stage>/local_data/`.
6. Produce diffs, applied to nothing:
   - `<stage>/venue_data_capability.diff`: the generated `earliest_ohlcv_utc` block, computed by `refresh_coin_start_dates.refresh` (`:277`) pointed at the staged files, plus a new symbol in `confirmed_universe` if one is added;
   - `<stage>/coin_universe.diff`: rows, span and within-life missing percentage, from the Q3 census run on the staged file;
   - `<stage>/manifest.yaml`: each staged file's SHA-256 and bytes; the SHA-256 and bytes of the file it would replace in the operator checkout; whether that file is tracked in git (all 38 `kraken_*_{1h,1d}.csv` are).

`data_ingest.py install --manifest <stage>/manifest.yaml --approved "<file list>"`
- Runs only when the operator's paste "install approved <file list>" names exactly the manifest's files. The command compares the two lists and refuses on any difference.
- Pre-image check: each target's current SHA-256 must equal the manifest's. If not, someone changed it since staging, and the command refuses.
- Copy into the checkout's `local_data/` through a temp file, an atomic rename, and a re-hash.
- The replaced file is kept as `<name>.pre-install-<UTC>` in `C:\Users\alauz\Documents\Projects\backups\local_data\`, so rollback is one copy.
- The capability and universe diffs are tracked config. They go in a normal PR, not into the checkout. Changes to tracked caches go in the same PR, so the checkout and master agree.
- The pipeline is unchanged: the run sees the files through the readers listed in 1.1.

## 5. Decisions for the operator

### Decision 0: the 1m source
- Recommended primary: the Kraken OHLCVT archive. 0 requests and 0 hours for the in-sample span, because it is on disk.
- Re-verifying the local copy against the published hashes means a download of about 10 GB, which needs disk space freed first.
- Recommended fallback: the REST Trades endpoint, for HYPE, for spans after the archive, and for spot checks. Cost per day: see 2.6.
- No paid source and no source needing a key.

### Decision 1: sealed-window bars from a fetch
- What the policy requires: nothing may read candles inside `holdout_range` except the holdout evaluation (`:8-9`). The only precedent for sealed bars arriving with a download is quarantine into `local_data/holdout_sealed/`, registered in the policy (`:167-184`).
- Recommendation:
  - (a) Every fetch stops strictly before the holdout start.
  - (b) Do not fetch sealed-window bars now. The sealed store already holds that tranche, and a second copy has no use until a holdout evaluation is scheduled. If one is scheduled, a named procedure downloads straight into `holdout_sealed/<tranche>/`, checks the published hash, adds a policy entry like `:177-184`, and never opens the files.
  - (c) Bars after the seal's end: the policy is silent and the code disagrees (1.4). Treat them as deny-by-default, like the forward recorder, until a dated designation.

### Decision 2: 1m storage format and layout
- Recommendation: per-coin, per-year Parquet (zstd), with a sidecar per file, read through one opt-in branch in `BaseFetcher._load_local` (2.4). Needs `pyarrow` in the venv.
- Fallback: the same layout as `.csv.gz`, with no new dependency.
- Size: 2.6.

### Decision 3: first real 1m backfill
- Recommendation: all 19 breadth pairs, the in-sample span, from the local archive copy.
- Cost: 0 requests; the hours are the ingest time (2.6 gives the rows).
- HYPE is absent from the archive. It needs the Trades loop from its listing to the exploration boundary, a separate "fetch approved".

### Decision 4: `fetch_interval_seconds=60`, or a one-time aggregation
- `fetch_interval_seconds` is a global switch in `trading-bot/config.json` (1.2). Setting it to 60 would move every campaign run onto the 1m store and replay about 60 rows per hourly bar.
- The current 1h and 1d caches are the archive's own 60- and 1440-minute files, already pinned by the hashes of past runs.
- Recommendation: keep the 1h and 1d caches as they are. Use the 1m store with `fetch_interval_seconds` only for timeframes the archive does not ship (for example 2h, 3m), set per run once that is wired.
- Prove the archive's 60m equals its 1m aggregated through `CandleBuilder`, once, and record it in the census. That gives one source of truth without rewriting pinned files.

### Decision 5: the per-run census
- Recommendation:
  - Campaign level: on demand, after every install, and dated.
  - Per run: on every run at the data gate stage, behind `orchestrator.data_census.enabled` (off by default), writing `artifacts/variants/<v>/data_census.yaml`. It costs seconds.
- Switch it on when the run viewer's data-gate card reads it.
