The three objectives

The ultimate goal is to find a profitable strategy. For that the research workflow is built to iteratively run backtest in order to prove ideas. The core thinking is that profitable strategies would come from an accumulation of proven ideas.

So a workflow iteration would be built around, taking an idea, building a strategy that would "test this idea" and see if idea is correct (objective 1)

But at the same time, i want this workflow to observe backtest output to see if we can find more ideas to come closer from a profitable strategy. For that it would take an overall set of metrics and launch llm analyzis on the set of metrics to find interesting patterns to deep dive or use in our profitability objectives (objective 2).

While the run should also at the end follow a test to see if the profitability is reached (thus the protocol, the promotion gate, etc..) - obejctive 3.

The pre/post-backtest vision

In my mind i have:

A prebacktest not so far from what we have currently local with:

  • a research brief that would bring a general topic to research OR a pre-made hypothesis / variant from another run
  • an hypothesis generation that would transform the research brief general topic into a testable hypothesis with acceptance factors. Or forward the hypothesis / variant as is if received as input
  • a variant generation stage that would create different variation of the testable hypothesis with the objective to create backtesting setup testing the same hypothesis. These variants generated would be designed in a sense that, tested in parrallel, they would allow to ensure that the verdict is linked to idea and do not depend on backtesting setup chosen.
  • Then we also have control ensure data variant need is available
  • And control on the variant itself (and hypothesis ?) to ensure that we are not testing a variant / hypothesis that has already been tested in the past.
  • Finally a loop allowing to design mechanical strategy config / setup the backtests and test each and every variants during backtest in a single run (but different backtest launch)

A post backtest design with three routes answering three questions:

  • 1/ is the idea (hypothesis) approved based on its acceptance criteria (here maybe mechanical if feasible), or LLM for now
  • 2/ Are the metrics generated giving some interesting patterns / ideas to be tested that would bring us closer from having a profitable strategy ? This root would be supported by multiple agents LLM analyst, each having their own respective area of focus (regime, signal, cost)
  • 3/ is any of the variant reaching the profitability goal that we would define globally and that would allow us to unlock the holdout backtesting stage.

These three branches should regroup for a last stage receiving inputs from each of the branch. This step should enrich the "memory" artifacts of the campaign (the history of all past and next runs) based on idea test results (branch 1), confirmed observation and patterns of specialist agents (branch 2). New brief can be created for patterns that would need to be tested (identified by branch 2). It should also record the score board that would be around profitability.

Then a next step taking the decision of "what's next" based on the campaign memory artifacts and profitability results

If profitability target are reached, a stop should be triggered and a manual review should happen.

The target design

agreed 2026-09-17/18 · the shared picture every card below builds toward

The brief's first sentence is the whole point: profitable strategies come from an accumulation of proven ideas. v24 had no step where anything accumulated. This board is organised around that missing piece. In plain words:

A
building blocks
One idea = one candidate building block. The goal of a run is to validate a block, not to find a profitable strategy on its own.

There are two kinds of block. A forecast block is a component, or a sub-strategy of weighted components, that produces a signal. A regime block is a detector rule that produces a label: it carries an idea about the market's overall state, and it changes how forecast blocks are combined (which sub-strategy is active under which regime). A regime block cannot be measured alone — only in combination — which is why it is validated as a composition variant (card F). A validated block is stored in a registry as its piece of bot config (the component entry with its parameters and weight and its regime assignment, or the detector rule), plus the criteria it passed, the variants it passed them on, and its measured numbers. A block must hold information: its forecast carries predictive power that the blocks already validated do not (measured as the residual information coefficient after regressing on the current composite forecast). Old runs' verdicts are legacy and do not populate the registry.

decided
B
two kinds of pass bar
Idea criteria are per hypothesis, from a menu, in scale-free units. Profitability bars are campaign-wide, written once by hand.

An idea's own pass criteria are chosen at hypothesis time (Step 1a) from an anchored menu of criterion types — information coefficient, correlation, sign consistency across eras, edge-to-cost ratio, regime-conditional effect, residual information — with anchored thresholds, the same way the plausible-IC table already anchors one number today. Every criterion is written in scale-free units, so it does not depend on which coin or which parameter value a variant uses: the type and the threshold are fixed once at 1a and applied identically to all variants; the only per-variant element is the measured sample against the declared floor. A criterion that cannot be written scale-free is refused at registration — a per-variant threshold would let a variant pick its own easy exam, and unanimity (card C) would mean nothing. Idea criteria are usually not about profit. The profit bars (Sharpe, max drawdown, average daily return, trade floor, deflated Sharpe) live in one manually written campaign file, which also declares the campaign's target instrument set; they apply to every backtest the same way and are hypothesis-blind.

decided
C
the grid
Branch 1 is a grid: criteria × variants, every cell mechanical, unanimity across variants. No LLM verdict, no averaging across variants, no re-thresholding per variant.

Windows inside one variant are repeated samples of the same setup, so they are aggregated — and each criterion type says how (median over windows, fraction of windows positive, same sign in every era, or pooled over all bars with the effective sample size). Variants are different setups, so they are never averaged: each must pass on its own, and the idea is validated only if every criterion holds on every variant. Every criterion carries a minimum sample floor; a variant under the floor gives an inconclusive cell, and the idea is inconclusive, not refuted. The default is one symbol per variant; a symbol reducer is declared only for cross-sectional ideas whose variant is a whole universe.

decided
D
three variants
Three variants per idea, cap four: the base design, one design variation, one asset variation on a coin from a different category.

Variants exist for one reason: to show the result does not depend on the backtesting setup chosen. Three covers the two ways a result can be setup-dependent. This retires the 2026-09-15 "no cap" note and folds E-026's asset-generalisability rule into the variant set. Every tested variant counts as one attempt for the deflated-Sharpe math; a variant dropped before data (data missing, component missing) is not an attempt.

decided
E
protocol = windows only
The protocol owns exactly one axis: the walk-forward test windows. Nothing else. Symbol, universe and timeframe are design fields; costs are a criterion.

Keeps separation of concerns clean: the protocol never chooses what to test, only when. Cost survival is a criterion, not a protocol axis: this bot's costs do not feed back into its decisions, so "survives 2× costs" is computable from one run's trade records (gross edge per trade against cost per trade) without any re-run. The cost figure is whatever the trade records carry. Today that is fees only — corrected 2026-09-20, built and verified while implementing CUL-300: slippage (E-010, done) genuinely reduces every trade's realized return at fill time, but the computed slippage_bps value itself is discarded rather than threaded through to the trade record, so it cannot be counted as a cost component yet (a small, well-scoped follow-up closes this — the number already exists at the exact right computation site). Sub-daily funding accrual is still open (E-053, backlog). v24's walkthrough claimed a cost-stress axis already existed; it never did.

decided
F
composition runs
Combining blocks is its own run, triggered in code whenever the registry changes, assembled by the LLM at Step 1b under the design guide, checked mechanically.

A composition run is an ordinary run whose idea is "the registry's blocks combine into a profitable strategy." Trigger: a rule in the decide-next step (Step 10): if the registry changed since the last composition run, the composition run is next — no LLM judgment. Generation: Step 10 writes a composition brief listing every eligible block from the registry and the three weighting schemes; Step 1a passes it through (its criteria are the profit bars); Step 1b's LLM assembles the config — this is real design work, not a merge, because a block can be a component, a sub-strategy, or a regime with its rule, and those do not combine on one scale; Step 5a then checks mechanically that every listed block is present in the config and that the weighting scheme was applied. Variants: the three weighting schemes (equal, volatility-scaled, IC-weighted). Instrument set: the campaign's target set from the profit-bars file. Cross-coin eligibility, decided 2026-09-19: a validated block is eligible for a composite on any instrument, not only the coins it was tested on — the composite's own result against the profit bars is the real check, not an upfront restriction. Scale, decided 2026-09-19: combining forecasts assumes they are on a comparable scale; rather than gating composition behind a separate epic, the design guide (Step 1b) is told to apply the transform pipeline's existing standardization op when assembling a composite. This is expected to already be sufficient. If a specialist reader (Step 7) finds otherwise from a real composite's results, that becomes an ordinary proposal in the queue — possibly reviving E-048 as a real build later, never a precondition now. Composition runs count their own trials. Regime ideas are tested the same way: variant A = the blocks ungated, variant B = the same blocks gated by the detector; the criterion is "B beats A on the bars while the label passes its health checks." The standing "no regime-gated hypotheses" rule is lifted for this.

decided
G
no more verdict routing
Refine / pivot / escalate / kill is retired. A run ends with an idea status — validated, refuted, inconclusive — and "what runs next" is a separate step.

The old verdicts were built for one lineage running alone: a failure automatically created the next run of the same idea. In the target design a refinement of a failed idea is just another candidate, proposed by a branch-2 reader, competing in the queue with everything else. The circuit breakers that stopped endless refines become queue policies. "Inconclusive" is reserved for data gaps and engineering failures and never counts as an attempt. The immediate child-run split that today launches extra hypotheses from one brief is retired with this (see card M).

decided
H
judge → learn → record → decide → park
Branches 1, 2 and 3 run in parallel on the same results. Then memory is written, then one step decides what runs next, then the rest are parked.

Memory is written before the decision so the decision is reproducible from what is on disk. Branch 3 (profit bars) is a check that runs on every backtest, variant or composite alike; when it passes, the loop stops and the operator regroups (card L). The holdout unlock stays a manual act after that stop.

decided
I
how the next idea is picked
Hybrid: mechanical gates, then three anchored LLM scores, then a trivial rank.

Gates are yes/no and in code: novelty (repeat checker, card K), feasibility (data gate, component exists), and the mandatory "registry changed → composition next" rule. Then the LLM scores each candidate on anchored 0–3 rubrics defined in a skill file — confidence the idea is real (3 = effect seen with effective sample above the floor and consistent across slices; 0 = story only), distance to a profitable strategy (3 = fills a missing block type with low correlation to the registry; 0 = neighbour of something already validated), and mechanism plausibility (who is on the other side of the trade, why it is not arbitraged away). Each score must cite its numbers; model id and rubric version are recorded. Ranking is then code: confidence, then distance, ties to the cheapest. Two readers proposing the same block collapse into one proposal with two sources. These scores pick what to test next; they never touch promotion. The operator can add a brief by hand at any time — a brief written from outside reading is a normal Step 0 entry; E-035 automates that later.

decided
J
component gap: park, don't stop
If a design needs a component the bot does not have, it is caught when the config is checked (Step 5a), the idea is parked with a written request, and the loop moves on.

There is no build backlog and none will be built. The gapped variant is "not tested" (not an attempt); a component request is appended to one file the operator reads (surfaced in the campaign summary); the other variants still run; if fewer than three remain the idea is parked as "waiting for component" in the queue, with the request attached, and becomes runnable again once the component exists. The loop stops only if nothing else is runnable. What the operator does then is a runbook row (card L).

decided
K
the config is the vocabulary
Step 1b writes the real bot config directly, under a design guide, plus a manifest and a short rationale. Variants are patches on it. Repeat = exact match. No translator layer.

Decided 2026-09-18 after weighing a separate "structured design document" against writing the config itself: a design that is already config-shaped plus a translator is a layer with a cost and no benefit. So: 1b's output is the actual strategy config file the bot runs, written by an LLM following a design guide (how a strategy config is to be designed: regimes, sub-strategies, weighted components, transforms, allocation), plus a manifest naming which entries in that config are the block under test and which are scaffolding, plus a prose rationale for humans. The config is the binding artifact. A variant (E-057) is a named patch on that config — one field changed. Step 5a needs no LLM: the existing config validator runs, a check confirms every component class exists in the bot, the manifest is checked against the config, and the three patched configs are assembled. A repeat (Step 4) is an exact match on the config hash plus instrument, timeframe and window set — anything else is a neighbour, attached as information, never refused. What is given up: a human-readable design layer separate from the config; the rationale field covers that cheaply. E-056's S1 measures what scaffolding an LLM adds beyond the hypothesis today, so the guide can constrain it.

decided
L
operator cases and the runbook
Every case where a human must act gets a runbook row: what to read, what to decide, which artifact to update, which command resumes the loop.

Three groups. Loop stops, operator acts: profit bars reached (review the composite; decide whether to spend the single-use holdout; run it by hand; record the outcome in the holdout result and the data-policy file; resume into Step 10 or promote); nothing runnable in the queue (write a new brief, or build a requested component, then resume); campaign review says stop. Idea parked, loop continues: component missing (card J); data missing for a variant (Step 3); an idea inconclusive twice for data reasons. Engineering halt, operator fixes and resumes: crash, conformance violation, invalid artifact — E-030 already covers these and the runbook already has a row per pause reason; the new rows follow the same format. Restart after any stop is the existing resume command: it clears the stop flag and re-enters Step 10. Documentation and the two new "parked" queue states are a named deliverable of plan item 11.

decided
M
briefs with several hypotheses
Step 1a may produce several hypotheses from one brief; one runs now, the others go to the queue with the brief as their source; the brief stays open until 1a says it is exhausted.

Today, several hypothesis cards from one brief become immediate child runs. In the target design they become queue candidates, scored like everything else. A brief carries a status, open or exhausted, set when Step 1a says it cannot honestly produce more from it. Before declaring the queue empty, Step 10 re-reads open briefs and asks 1a for more. Small evolution — a queue entry shape and one rule — but a real one: tracked in Linear as a sub-issue of E-031 (plan item 12), not left implicit.

decided
N
one entry point
Every candidate enters at Step 1a, whatever its source. A candidate that already carries a config and criteria passes through with a completeness check only.

A reader's proposal from Step 7 is recorded at Step 9, ranked at Step 10, parked at Step 11, and when picked it enters at Step 1a like a fresh brief. Because it already carries a structured design and criteria, 1a and 1b only verify completeness — they never redo the work. Same for a composition brief (card F) and for a parked idea whose missing component now exists. This pass-through rule is part of E-056's scope. The former validation stage between Step 2 and Step 5 is deleted, not folded anywhere: its historical catches were design mistakes to fix in the design guide, and it was controlling a problem that should not exist.

How the pipeline works, step by step

14 steps + 3 notes · plain-language walkthrough · now / what changes / target

Imagine you're teaching a trading robot to get smarter over time. It doesn't just trade — first, it has to figure out what actually works, by testing ideas one at a time, like a scientist running experiments. Here's every step of that experiment-running process, in order: what it's for, how it works today (checked against the code on 2026-09-16), what changes, and what the target looks like — each one tagged with the epic that owns it. The one-line version of the target: write the idea as a real config → test it three ways → grade it with a grid → learn from it → write it down → decide what's next → park the rest → combine what was proven.

Step 0

Where does an idea come from?

Objective
Give the system a starting point: either "go explore this general area," or a specific, already-shaped idea handed to it. A brief may contain several ideas worth testing.
Today
A person writes the starting topic. After a run, the system's "refine" or "pivot" verdict writes the next brief itself and creates the next run immediately, without anything choosing between candidates. If hypothesis generation produces several cards from one brief, each becomes a child run immediately.
What changes
Ideas arrive from more sources — the specialist readers (Step 7), campaign review, the operator writing a brief from outside reading (a normal entry today; E-035 automates it later) — and every one of them goes through the same queue and the same decide-next step (Steps 10–11). No source creates a run directly any more. A brief with several ideas puts one in the run and the rest in the queue, and stays open until Step 1a says it is exhausted (card M).
Target
One doorway, many sources, one rule for who goes first, and no idea in a brief is ever forgotten.

Epic: No dedicated epic. Fed by E-032 (done), E-035 (plan item 15) and the readers of E-046a (item 8); governed by items 11–12 (brief status: a sub-issue of E-031).

Step 1a

Turning the idea into a testable hypothesis, with its own pass criteria

Objective
Take an idea — from a brief, from a reader's proposal, from a composition brief, from an un-parked candidate: this is the single entry point for every candidate (card N) — and turn it into a precise claim that can be proven right or wrong, plus the rule for "right," written down before any test runs. The rule is usually not about profit: it is about the mechanism — a real signal, that survives costs, that carries information the proven blocks do not already have (card B). If the candidate already carries a config and criteria, this step only checks completeness and passes it through.
Today
An AI writes the hypothesis from scratch every time, including for a refine child that already had one. The pass rule does not come from this step: it is copied from the human brief when the run is created, or from the previous run's AI-written proposed brief. Only 3 of the 10 runs that have a pre-registration file carry a structured rule; the rest are prose that the checker cannot address.
What changes
This step chooses the criteria from the anchored menu (owned by item 7): criterion types with anchored thresholds, all in scale-free units, so they apply unchanged to every variant whatever its coin or parameters — pick from a table, don't free-hand — and the idea's author cannot write itself an easy exam. Profit bars are never chosen here (they are campaign-wide, Step 8). Already-formed candidates pass through.
Target
Every hypothesis arrives with criteria a machine can check, chosen from a fixed vocabulary, identical across its variants.

Epic: E-056 (item 4), part 1a, including the pass-through rule. CUL-267 (item 1) guarantees an unmatchable or non-scale-free criterion is refused here rather than skipped later. The menu itself: E-046b (item 7).

Step 1b

Writing the real bot config, under the design guide

Objective
Produce the actual strategy config the bot will run — which regime it applies in, which component or sub-strategy, with which parameters and weight, on which symbol or universe, at which timeframe — written by an LLM that follows a design guide on how a strategy config is to be designed, plus a manifest naming which entries are the block under test and which are scaffolding, plus a short rationale for humans (card K). For a composition brief, this is where the registry's blocks are assembled into one strategy — a real design task, since a block can be a component, a sub-strategy, or a regime with its rule (card F).
Today
The design is described in loose labels (a category, a "diversity axis"). The real config is invented later by the config-building step, invisibly, worst of all when refining a failed idea, where it does not even receive the exact setup that ran last time.
What changes
The config is written here, once, and becomes the binding artifact. There is no separate design document and no translator. A regime's strategy assignment can explicitly be "none." The instrument set is a field: one symbol by default, a named universe for cross-sectional ideas.
Target
What runs is exactly what this step wrote, and the manifest says which part of it is the idea.

Epic: E-056 (item 4), part 1b and the design guide.

Step 2

Making three versions of the same idea, as patches on the config

Objective
Test the idea three ways so that if it works, it is the idea that is good, not one lucky setup: the base config, one design patch (a parameter neighbour or a different component form), one asset patch (a coin from a different category) (card D). Each version is one named field change on Step 1b's config. The same three criteria from Step 1a apply to all three, unchanged.
Today
Several versions get proposed; exactly one is tested; the rest are recorded as "not pursued" and thrown away. Versions are described by category labels, not as a precise change.
What changes
All three are tested. Each is a patch. Each tested one counts as an attempt for the deflated-Sharpe math. This step only generates; it does not check for repeats (that is Step 4).
Target
Three configs that differ from each other in exactly the one way each was meant to.

Epic: E-057 (item 5) for the patch; E-033.1 (item 6) for testing all three.

Step 3

Checking the data exists, once per version

Objective
Before a slow test, a quick check: do we even have the price history each version needs?
Today
Built and tested (E-054), but switched off by default behind an environment variable the campaign runner never sets, and missing from the feature-flag register. In a real campaign it does not run. When it does run and data is only partly there, it pauses the whole loop for a human.
What changes
Switched on by default, registered, and run once per version. A version whose data is missing is "not tested" and does not count as an attempt; if fewer than three versions remain the idea is parked as "waiting for data" and the loop moves on (card J's pattern; runbook row in card L).
Target
No backtest ever starts on data that is not there, and a data gap never stops the whole loop.

Epic: plan item 14 (E-054 follow-up, absorbs E-054.1).

Step 4

Checking we haven't already run this exact setup, once per version

Objective
Don't spend a real experiment on a setup that already ran. A repeat means the exact same full setup: same config, same instrument, same timeframe, same window set. If any element differs — strategy, a parameter, the coin — it is not a repeat; it is a neighbour, and the neighbour's result is attached as information. This is the only place that check happens.
Today
The gate exists in code and is switched off. Its first "same thing" test was rejected on design because it treated a strategy as a flat bag of parts.
What changes
Because Step 1b writes the config itself, the check is a hash comparison. Old verdicts are tagged legacy and never cause a refusal: "failed" under the old rules meant "not profitable alone," which says nothing about whether the block holds information.
Target
Exact repeats are refused; everything else runs, better informed.

Epic: E-036 (item 13), shrunk to exact match.

Step 5a

Checking and assembling the configs — no LLM

Objective
Take Step 1b's config and Step 2's patches and make three runnable configs. Validate each with the existing config validator, confirm every component class exists in the bot, confirm the manifest matches the config (for a composition run: every listed block is present and the weighting scheme applied), and refuse loudly on anything else. If a component is missing, catch it here (card J).
Today
An AI writes the config and fills every unstated detail itself. The schema validator then checks the result. A "component gap" path exists but relies on the AI noticing, and it pauses the run for a human.
What changes
No design happens here any more; it all happened in 1b. This step is validation and patch application, in code. A missing component marks the version "not tested," writes a component request to the operator's file, and the other versions still run (fewer than three left → the idea is parked "waiting for component"; the loop moves on).
Target
The config that runs is exactly the one written in 1b plus one named patch, or the run refuses.

Epic: E-056/E-057 (items 4–5); parked states and the request file in item 11.

Step 5b

Running the protocol: the test windows

Objective
Run each version across many time windows (walk-forward). The protocol owns only this one axis; it never chooses what to test and never varies anything but the windows (card E). Costs are not re-run: they are read off the trade records by a criterion (Step 6).
Today
Monthly windows only, generated from the run's pre-registered constraints; 14 metrics recorded per window. The escalate route can pick a new coin or timeframe on its own — that goes away with Step 10.
What changes
Loop over the three versions inside the same protocol run. Nothing else.
Target
One run = three versions × all windows, all recorded per window in one table.

Epic: E-033.1 (item 6) for the version loop.

Step 6

Grading the idea: the grid (branch 1)

Objective
Decide, from the numbers alone, whether the idea passed the criteria it declared in Step 1a — on every version, not on one lucky one (card C). Cost survival is one of those criteria, computed from the trade records (fees, funding, slippage as recorded), not from a re-run.
Today
A mechanical checker exists and is meant to be binding, but it has produced a binding verdict on 1 run out of 60; everywhere else the AI's own judgment decided. A criterion can only name 4 hard-coded per-version numbers. Nothing checks whether the versions agree.
What changes
Rows are criteria, columns are versions, each cell is measured: the windows inside a version are reduced the way the criterion says (median, fraction positive, same sign per era, or pooled), and every criterion has a sample floor. Thresholds are never adjusted per version. The idea is validated only if every cell passes, refuted if any cell fails with enough data, inconclusive if any cell is under its floor. The AI explains; it never overrules.
Target
A verdict nobody can argue with after the fact, because the rule was written before the run and applied by code.

Epic: E-046b (item 7, CUL-298 merged in, owns the menu); CUL-267 (item 1) as its prerequisite; cost-survival criterion (item 3).

Step 7

Learning from the results: mechanical reports, specialist readers (branch 2, runs alongside Step 6)

Objective
Separately from pass/fail: code computes five focused reports from the raw per-window table (profitability, trade efficiency, forecast power, regime power, component attribution, each sliced overall / per window / per regime / per symbol), and one LLM reader per report proposes new ideas, win or lose. Readers can only suggest, never decide.
Today
One generalist AI does grading, explaining and suggesting all at once. A "how close did other attempts get" scoreboard exists but the loop never calls it. A regime auditor is documented as a stage and never dispatched.
What changes
Reports are code; readers are agents. Each proposal is written as a config patch or a block sketch in the design-guide vocabulary and carries three anchored scores (card I) so Step 10 can rank it in code. The regime auditor's judgment role is gone: its "label beats ignoring it" check is now a criterion for regime blocks (Step 6), its lag and health numbers are metrics in the regime-power report, and its firewall is a reader rule.
Target
A failed experiment still produces a good next idea, and that idea arrives ready to be ranked.

Epic: E-046a (item 8). Calibration caveats trace to E-047 and E-048 (both backlog — E-048 is no longer a plan item, see the composition note).

Step 8

Checking the profit bars (branch 3, runs alongside Steps 6 and 7)

Objective
Check every backtest that ran — a version, or a composition — against the campaign-wide profit bars, which are the same for every idea and written once by hand (card B). If they clear, stop the loop and tell the operator.
Today
A promotion audit with a deflated-Sharpe check and a holdout route exist in code, but no run has ever reached them; profit thresholds live per protocol file with a ratification guard around them; you would only learn the bar cleared by checking a file.
What changes
One profit-bars file; the check runs on every backtest; a pass stops the loop loudly for a manual regroup, with a runbook row saying what to read, what to decide, what to update. The holdout unlock is not part of this step.
Target
The moment something clears the real bar, a human knows, and nothing automatic happens next.

Epic: profit-bars ticket (item 2).

Step 9

Regroup and record

Objective
Write everything down before anything is decided: the idea's status and grid, the block registry (a validated block enters here, as its config fragment), the attempt rows, the readers' proposals, and the scoreboard (card H).
Today
Four separate habits: a knowledge-base entry per run, an auto-generated carry-over note, one attempt row per run, and a scoreboard script nobody calls.
What changes
One explicit stage that records and stops. It decides nothing.
Target
Everything Step 10 needs is on disk, so its decision can be replayed and audited.

Epic: regroup epic (item 10); block registry (item 9).

Step 10

Deciding what runs next

Objective
One place, one rule: read memory and the queue, apply the gates, the scores and the rank of card I, and pick the next run. Two code rules come first: if the block registry changed since the last composition run, the composition run is next and this step writes its brief from the registry (card F); if the queue is empty, ask any open brief for more hypotheses before stopping (card M).
Today
Three different things decide: the run's own verdict creates a child run immediately (refine/pivot/escalate), campaign review fires every six runs or after two family failures, and the queue is never consulted while a lineage is alive.
What changes
Verdict routing is retired. Campaign review keeps only the strategic question (change the research question, or stop). Every candidate — a reader's proposal, a refinement, a brief's extra hypothesis, an outside idea, an un-parked idea — competes here on the same scores. After any stop, the resume command re-enters here.
Target
The next run is always the best-ranked candidate, and the reason is recorded.

Epic: verdict-retirement epic (item 11); E-031 (item 12).

Step 11

Parking the rest

Objective
Everything Step 10 did not pick waits in one queue, in the design-guide vocabulary, with its scores, until it is picked or refused. Ideas waiting for a component or for data wait here too, with their request attached.
Today
The only way to add a new line of inquiry is a hand-run command, used twice in the system's history. When the last lineage ends, the loop stops and stays stopped.
What changes
One queue for every source; no cap on how many wait; a candidate is re-scored when memory changes; two new parked states with their runbook rows.
Target
Good ideas never vanish because another one ran first, or because a component was missing that day.

Epic: E-031 (item 12); parked states in item 11.

Step 12

The final exam, after a manual stop

Objective
When Step 8 has stopped the loop and the operator agrees, spend the single-use holdout on the composition that cleared the bars. Looking is spending: it happens once, by hand, on purpose. Afterwards the operator records the outcome (holdout result, data-policy consumption marker) and either promotes or resumes the loop into Step 10 to keep adding blocks.
Today
Single-use enforcement, the deflated-Sharpe gate and the "is this even tradable" check exist in code and have never been exercised by a real run. The holdout backtest itself must be run by a person.
What changes
Nothing mechanical. It reads the profit-bars file instead of per-protocol thresholds, and it is reached only through Step 8's stop plus a human decision, with a runbook row for the whole procedure.
Target
Same safety, now actually reachable, and the way back into the loop is written down.

Epic: No epic; profit-bars ticket (item 2) changes what it reads; runbook row in item 11.

Composition runs — where proven ideas accumulate

What it is
A run whose "idea" is "the registry's validated blocks combine into a profitable strategy." Who triggers it: Step 10, by a code rule, whenever the registry changed since the last composition run. How it is generated: Step 10 writes a composition brief listing every eligible block (forecast blocks with their regime assignments, regime blocks with their rules) and the three weighting schemes; Step 1a passes it through with the profit bars as criteria; Step 1b's LLM assembles the config under the design guide — a design task, not a merge, because blocks live at different levels (component, sub-strategy, regime rule) and are not on one scale; Step 5a checks every listed block is present and the scheme applied. Its three versions are the weighting schemes. It goes through Steps 3–11 like any other run and counts its own attempts. It trades the campaign's target instrument set from the profit-bars file.
Today
Does not exist. Every run tests one idea alone and nothing ever combines two proven ones.
Decided 2026-09-19
A block is eligible for a composite on any instrument, not only the coins it was tested on — the composite's own grading against the profit bars is the real check. Combining forecasts assumes a comparable scale; the design guide applies the existing transform pipeline's standardisation when assembling a composite rather than waiting on a separate epic (E-048) — that epic is only revived if a specialist reader's real finding says the existing transforms are not enough.

Epic: block registry and composition (item 9). E-048 stays in the backlog unless a reader's finding promotes it.

Note

Regime ideas — a second kind of building block, tested as composition versions

What it is
A regime block carries an idea about the market's overall state. It has no value alone; it has value only when some forecast blocks behave differently by regime. So a regime idea is a composition run with two versions: the blocks ungated, and the same blocks gated by the detector. The criterion: the gated version beats the ungated one on the bars, and the label passes its health checks (persistence, flip rate, sensitivity to a small parameter nudge, and the hindsight-lag comparison — whose hindsight labeller must never reach a signal). A validated regime block enters the registry like any other block, as its detector rule.
Today
A standing rule forbids regime-gated hypotheses because the detector was judged unusable on BTC/ETH 1h; a regime auditor is documented and never runs.
How the loop finds them
The regime reader (Step 7) sees per-regime slices of a block's results — say, a strong effect in high-volatility bars and none elsewhere — and proposes the gated version. That is as far as the loop's cleverness goes, and it is enough.

Epic: item 9 (composition) and item 8 (regime reader, absorbing E-040's measurements).

When a human must act — the runbook

Loop stops
Profit bars reached: read the composition's grid and reports; decide whether to spend the holdout; if yes, run it by hand, write the holdout result and mark the holdout consumed in the data-policy file; then promote, or resume into Step 10 to keep adding blocks. Nothing runnable: read the queue summary (parked ideas and their requests); write a new brief, or build a requested component and un-park its idea; resume. Campaign review says stop: read its rationale; decide; resume or close the campaign.
Idea parked, loop continues
Component missing: the request file names the component and the idea; build it when convenient; un-park. Data missing: the request names the feed and window; fetch or route to the feed lane; un-park. Inconclusive twice for data reasons: same as data missing, flagged for attention.
Engineering halt
Crash, conformance violation, invalid artifact: fix at the site named in the halt record, write the resolution artifact, resume — as E-030 already documents, one row per reason.
Each row states
What to read, what to decide, which artifact to update, and the command that resumes the loop into Step 10.
